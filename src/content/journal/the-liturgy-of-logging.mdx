Your logs are lying to you.

Not maliciously. They're lying by **omission** — the context that was obvious when you wrote the log line, gone when you need it at 3 AM. They're lying by **volume** — the needle buried in a haystack you built yourself. They're lying by **structure** — JSON that parses but doesn't *tell*.

**Logs are not for debugging. Logs are for *investigation*.**

The difference: debugging assumes you know what you're looking for. Investigation assumes you *don't*.

---

## The Three Sins of Logging

### 1. The Sin of Context Stripping
```typescript
// ❌ The developer's view (context-rich)
logger.info('Payment processed', { orderId, amount, currency });

// ❌ The 3 AM view (context-stripped)
{ "level": "info", "msg": "Payment processed", "orderId": "ord_7x9k2", "amount": 29900 }
// Where's the customer? The payment method? The idempotency key? The retry count?
```

### 2. The Sin of Level Abuse
```typescript
// ❌ Everything is "info" or "error"
logger.info('User logged in');
logger.info('Cache miss');
logger.info('Database connection acquired');
logger.error('Payment failed'); // Same level as "disk full"
```

### 3. The Sin of the Orphaned Line
```typescript
// ❌ No correlation ID, no trace ID, no span ID
{ "msg": "Retrying payment", "attempt": 2 }
// Which payment? Which order? Which customer? Which trace?
```

## The Liturgy: Designing for the Investigator

This ritual designs logging **from the 3 AM perspective backward**.

### Phase I: The Corpus (Structure)

Every log line **must** carry:

```typescript
interface LogEntry {
  // Identity — who, what, where
  timestamp: string;           // ISO 8601, UTC, nanosecond precision
  level: 'trace' | 'debug' | 'info' | 'warn' | 'error' | 'fatal';
  service: string;             // 'payment-api', 'order-worker', etc.
  version: string;             // Git sha / release tag
  
  // Correlation — the thread that binds
  traceId: string;             // W3C traceparent / B3
  spanId: string;              // Current span
  parentSpanId?: string;       // For linking
  
  // Intent — why this line exists
  event: string;               // Stable event name: 'payment.initiated', not 'Processing payment...'
  message: string;             // Human-readable, *supplementary* to event
  
  // Context — the world at this moment
  context: Record<string, unknown>; // Structured, queryable, *complete*
}
```

**The rule:** If you'd need it to understand this line at 3 AM without reading code, it goes in `context`.

### Phase II: The Taxonomy (Levels)

| Level | Meaning | Example | Retention |
|-------|---------|---------|-----------|
| `trace` | Execution flow (function entry/exit) | `cache.lookup.start` | 1 hour |
| `debug` | Diagnostic detail for active investigation | `query.plan.analyzed` | 24 hours |
| `info` | **Business events** — things stakeholders care about | `order.placed`, `payment.succeeded` | 90 days |
| `warn` | **Degradation** — system still works but impaired | `retry.attempt`, `cache.miss`, `fallback.activated` | 90 days |
| `error` | **Failure** — operation failed, user impacted | `payment.declined`, `webhook.timeout` | 1 year |
| `fatal` | **Catastrophe** — system cannot continue | `db.pool.exhausted`, `config.missing` | Forever |

**Critical distinction:** `info` = *business happened*. `warn` = *system struggling*. `error` = *user hurt*. `fatal` = *system dying*.

### Phase III: The Events (Vocabulary)

Adopt a **stable event vocabulary**. Not free-form messages. Events are *queryable nouns*.

```
# Good events (stable, queryable, namespaced)
order.created
order.cancelled
payment.initiated
payment.succeeded
payment.failed
payment.refunded
inventory.reserved
inventory.released
email.queued
email.sent
email.bounced
webhook.received
webhook.processed
webhook.failed
cache.hit
cache.miss
rate_limit.exceeded
circuit_breaker.opened
circuit_breaker.closed

# Bad events (unstable, unqueryable, narrative)
"Creating new order for user"
"Payment went through okay I think"
"Something weird with the cache"
"Retrying because it failed"
```

**Every event name is a contract.** Change it → break dashboards, alerts, investigations.

### Phase IV: The Context (Completeness)

For each event, define **required context fields** — the minimum viable investigation kit.

```typescript
// Event: payment.succeeded
// Required context:
{
  paymentId: string;
  orderId: string;
  customerId: string;
  amount: number;           // Minor units (cents)
  currency: string;         // ISO 4217
  method: 'card' | 'bank' | 'wallet';
  provider: 'stripe' | 'adyen' | 'paypal';
  providerPaymentId: string;
  idempotencyKey: string;   // Critical for deduplication
  retryCount: number;       // 0 = first attempt
  latencyMs: number;        // End-to-end
  riskScore?: number;       // If fraud check ran
}
```

**Enforce at compile time.** Use a schema registry. Reject log lines missing required fields.

### 2. The Trace Context (Async Local Storage)

```typescript
// lib/logging/trace-context.ts
import { AsyncLocalStorage } from 'async_hooks';

interface TraceContext {
  traceId: string;
  spanId: string;
  parentSpanId?: string;
}

const traceStorage = new AsyncLocalStorage<TraceContext>();

export function runWithTraceContext<T>(
  traceContext: TraceContext,
  fn: () => T
): T {
  return traceStorage.run(traceContext, fn);
}

export function getTraceContext(): Partial<TraceContext> {
  const ctx = traceStorage.getStore();
  if (!ctx) return {};
  return {
    traceId: ctx.traceId,
    spanId: ctx.spanId,
    parentSpanId: ctx.parentSpanId,
  };
}

// Middleware for incoming requests
export function traceMiddleware(req: Request, res: Response, next: NextFunction) {
  const traceId = req.headers['traceparent']?.split('-')[1] || crypto.randomUUID();
  const spanId = crypto.randomUUID().slice(0, 16);
  const parentSpanId = req.headers['traceparent']?.split('-')[2]?.slice(0, 16);
  
  runWithTraceContext({ traceId, spanId, parentSpanId }, () => {
    // Bind trace context to response headers for downstream
    res.setHeader('traceparent', `00-${traceId}-${spanId}-01`);
    next();
  });
}
```

### 3. Usage in Code

```typescript
// services/payment.ts
const logger = createLogger('payment-api', process.env.VERSION!);

async function processPayment(input: PaymentInput) {
  return runWithTraceContext(
    { traceId: input.traceId, spanId: crypto.randomUUID().slice(0, 16) },
    async () => {
      const log = logger.child({ paymentId: input.idempotencyKey });
      
      log.info('payment.initiated', 'Payment processing started', {
        orderId: input.orderId,
        customerId: input.customerId,
        amount: input.amount,
        currency: input.currency,
        method: input.method,
        idempotencyKey: input.idempotencyKey,
        retryCount: input.retryCount || 0,
      });
      
      try {
        const result = await chargeCard(input);
        
        log.info('payment.succeeded', 'Payment completed successfully', {
          providerPaymentId: result.id,
          provider: 'stripe',
          latencyMs: result.latencyMs,
          riskScore: result.riskScore,
        });
        
        return result;
      } catch (error) {
        log.error('payment.failed', 'Payment failed', {
          errorCode: error.code,
          errorMessage: error.message,
          retryable: error.retryable,
          latencyMs: Date.now() - startTime,
        });
        throw error;
      }
    }
  );
}
```

## The Vigil: Querying the Liturgy

With this structure, your 3 AM queries become trivial:

```sql
-- All failed payments for customer in last hour
SELECT * FROM logs 
WHERE event = 'payment.failed' 
  AND context.customerId = 'cus_abc123'
  AND timestamp > NOW() - INTERVAL '1 hour';

-- Retry patterns for failed webhooks
SELECT context.retryCount, COUNT(*) 
FROM logs 
WHERE event = 'webhook.failed' 
  AND timestamp > NOW() - INTERVAL '24 hours'
GROUP BY context.retryCount;

-- Latency degradation for payment.succeeded
SELECT percentile_cont(0.99) WITHIN GROUP (ORDER BY context.latencyMs)
FROM logs 
WHERE event = 'payment.succeeded'
  AND timestamp > NOW() - INTERVAL '1 hour';
```

## The Confession

We didn't always log this way.

Three years ago, our logs were `console.log` statements with emoji. 🚀✨💥

The migration took **six months**. We did it service by service. Event by event. The old logs still exist in cold storage — we query them *once a year*.

**But the first time this liturgy saved us — a payment regression caught in 4 minutes instead of 4 hours — the investment paid for itself.**

## The Invitation

**Audit your logs tonight.**

Pick one critical path. One event type. Ask:

1. *If this line appeared at 3 AM with no other context, could I understand what happened?*
2. *Does it have a stable event name I can query?*
3. *Does it carry the correlation IDs to trace the full request?*
4. *Is the level honest about business impact?*

If the answer is no — **rewrite that one event.** Just one.

Then the next. Then the next.

**The liturgy is not a migration. It's a practice. You build it line by line, night by night.**
